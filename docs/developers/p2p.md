# Reaching Arcanist through the P2P network

Arcanist servers can be reached from anywhere without opening ports, through a peer-to-peer network built on
[iroh](https://www.iroh.computer). A server's administrator turns it on in the panel (**P2P network**); users then
pair their devices from **My account → My devices**, and administrators can share libraries with other Arcanist
servers.

Traffic is end-to-end encrypted (QUIC with TLS 1.3, keys pinned to each node's id). When two nodes cannot connect
directly, it goes through a relay: n0's public relays by default, or one the administrator runs. Relays only see
that two nodes talk, never what they say.

This guide is for apps. Everything after pairing is the usual API ([README.md](README.md)): the P2P network only
replaces the server's address.

## The native library

`native/arcanist-p2p` (Rust) does the networking, with bindings for Swift and Kotlin generated by
[uniffi](https://mozilla.github.io/uniffi-rs/):

```bash
cargo build --release --features mobile --manifest-path native/arcanist-p2p/Cargo.toml --target <your target>
cargo run --features bindgen --bin uniffi-bindgen --manifest-path native/arcanist-p2p/Cargo.toml -- \
    generate --library native/arcanist-p2p/target/<your target>/release/<the built library> \
    --language kotlin --language swift --out-dir <dir>
```

It exposes:

- `generate_secret_key()`: 32 bytes. **Generate it once and keep it** (in the keychain or keystore): it is the
  device's identity, and a server recognizes a paired device by it.
- `parse_invitation(uri)`: reads an invitation link (see below).
- `ArcanistP2p(secret_key, relay, relay_url)`: a node that only connects. `relay` is `n0` (the default),
  `custom` (with `relay_url`) or `direct`.
  - `connect(ticket, timeout_ms)`: opens a local TCP port that tunnels to the server, and returns it. The first
    connection is made right away, so an unreachable server fails here (`unreachable`). Afterwards the tunnel
    reconnects by itself when the network changes.
  - `disconnect(port)`, `node_id()`, `close()`.

Errors are short codes: `unreachable`, `invalid_ticket`, `invalid_invitation`, `own_ticket`, `closed`…

## Invitations

The server shows invitations as a QR code and a link:

```
arcanist://p2p?kind=device&node=<ticket>&token=<token>&name=<server name>
```

- `kind` is `device` (pair a device with a user) or `share` (for another server).
- `node` is the server's ticket (its node id and addresses, as base64url JSON); `parse_invitation` returns it as
  the JSON `connect` takes.
- `token` is for one use, and expires: 30 minutes for devices, 7 days for shares.

## Pairing a device

1. Scan the QR code and read it with `parse_invitation`. Keep `ticket` and `name`: they are how the app finds this
   server from now on.
2. `connect(ticket)` and use `http://127.0.0.1:<port>` as the server's address.
3. Pair: `POST /rest/v1/p2p/pair` with `{"token": "<token>", "name": "<this device's name>"}`. It answers
   `{"serverName": "…", "peerId": "…"}`; `403 invitation_invalid` when the token was used or expired.
4. Sign in as usual (`POST /rest/v1/auth/login`), and use the API. The user sees the device in **My devices**, and
   can revoke it there.

Later, connect with the kept ticket: there is no need to pair again. A server's node id never changes; its
addresses may, and the n0 relay finds it by its id alone.

## What can go wrong

Through the P2P network, besides the usual errors:

| Status | Code | Meaning |
|---|---|---|
| 403 | `peer_unknown` | The device is not paired (or was paired with another server). |
| 403 | `peer_revoked` | The user or an administrator revoked it: pair again with a new invitation. |
| 403 | `peer_expired` | Its access ended. |
| 429 | `too_many_streams` | Too many audio streams at once, for this device or for everyone. |
| 403 | `download_not_allowed` | The administrator does not allow downloads through the P2P network. |

An administrator may also cap the bit rate for a device: audio then arrives converted (MP3 unless the app asks for
another format), even if the app did not ask for it. Bandwidth may be limited too, so prefer streaming to
downloading whole files ahead.

The server sees requests through the P2P network as coming from the internet, never from its local network: the
setup code is always required, and DLNA does not answer.

## Between servers

When a server accepts a share, its library "… library" is described by the server that shares it
(`GET /rest/v1/peer/files`, 500 files at a time, with their tags and content hash) and its audio is streamed from
it on demand (`GET /rest/v1/peer/stream`), under the rules the owner set. When the owner allows downloads, the receiving server's administrator can also copy
the files into one of its own libraries. These endpoints, tagged "Peer" in the
OpenAPI document, only answer servers through the P2P network; apps never use them.
